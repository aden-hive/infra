Hive SaaS — control plane + cloud/desktop data planes, Hive runtime shared

Three pieces layered together: (1) the existing aden-hive SaaS control plane on GKE — auth, users, teams, API keys, billing, tsdb. (2) a deployment-mode switch that routes each session to either the cloud data plane (Firecracker microVMs on OVH — live as of 2026-04-22) or the desktop data plane (Electron app on the user's machine). (3) the Hive runtime — the agent harness itself (framework + tools + commercial + extension) — which runs inside both data planes. Source code spine, three packaging variants.

Integration: two runtime paths, one control plane

aden-hive on GKE is the sole identity provider and billing system. The deployment-mode switch on the team/user decides which data plane handles a new session; both planes report usage back through the same pipe.

Cloud path (mode = cloud) — steps 3-5 live on OVH today

  1. TODO: User calls POST /api/sandboxes on aden-hive with JWT / API key.
  2. TODO: Sandbox controller validates team + quota, creates a Postgres row, then calls the OVH orchestrator (mTLS / signed request, JWKS from aden-hive).
  3. LIVE: OVH orchestrator resumes a Firecracker microVM from the template's memfile snapshot in ~50ms; writes back host + sandbox_id.
  4. LIVE: Orchestrator proxy (:5007) routes E2b-Sandbox-Id + E2b-Sandbox-Port headers to the right VM's internal port. TODO: edge layer that maps <id>.sandbox.hive.com onto these headers.
  5. TODO: Sandbox events (boot, idle, hibernate, exit) and per-LLM-call usage stream to aden-hive's unified usage ingest; TimescaleDB rollups drive billing.

Desktop path (mode = desktop)

  1. User installs the desktop app hive-desktop (signed Electron bundle). First launch runs device-code OAuth against aden-hive → app receives refresh token, persists to OS keychain.
  2. Electron main process (src/main/runtime.ts) spawns the bundled hive-desktop-runtime Python subprocess on 127.0.0.1. Renderer talks to it over IPC + SSE (src/main/sse.ts, ipc.ts).
  3. App prompts user to install Hive Browser Bridge from Chrome Web Store (one-time, deep-linked).
  4. App polls GET /api/entitlement every ~10 minutes: receives short-lived JWT, allowed model list, remaining LLM quota, feature flags (including which commercial modules activate for this plan), revoke flag. Enforces locally.
  5. When the user runs an agent, no sandbox is provisioned anywhere — the runtime subprocess runs it in-process on their machine and drives the user's Chrome via the extension.
  6. App batches usage events (LLM tokens, active-agent-seconds, tool invocations) and POSTs them to the same unified usage ingest every N seconds. Offline events are buffered to disk and replayed when online.
  7. If aden-hive sets the revoke flag (plan lapsed, user removed, incident response), the next entitlement poll disables the runtime's agent loop on the desktop.

Auto mode (mode = auto)

Default for users with a paired desktop and a plan that allows cloud. The sandbox controller picks: desktop if the paired client heartbeated in the last 60s AND the agent task doesn't require the sharing features (watch via URL, team concurrency); cloud otherwise. Decision is stored on the session row for observability.
